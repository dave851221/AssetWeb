# AssetWeb

在 GitHub Pages 上的個人資產儀表板。讀取你自己 Google Drive 上的 `AssetSync.xlsx`，
在瀏覽器內解析並分析——沒有後端，沒有資料庫，資料不會離開你的電腦。

權限完全交給 Google：檔案沒分享給你，你的 Google Picker 就看不到它，
所以這個網站不需要維護任何白名單。

## 這是什麼、資料從哪來

[AssetSync](../AssetSync) 每天從富邦、永豐、IBKR 抓取帳戶資料，用 openpyxl 產出
`AssetSync.xlsx`，再由 `extensions/backup_to_gdrive.py` 複製到
Google Drive 的同步資料夾。**它產出的不是原生 Google Sheet**，所以本專案是用
Drive API 把 xlsx 的 bytes 抓回來，在瀏覽器裡用 SheetJS 解析，
而不是走 Sheets API。

選 xlsx 而不是 AssetSync 同時匯出的那些 CSV，理由有三：不用改 AssetSync、
Picker 只需選一個檔案、而且 `manual` 分頁刻意不匯出 CSV——只有 xlsx 裡有。

## 架構

零建置：沒有 npm、沒有 bundler、沒有框架。原生 ES modules，
`index.html` 只有一個 `<script type="module">`。

**所有路徑都是相對路徑**，所以 GitHub Pages 的子路徑（`/asset-web/`）
與 localhost 都不用任何設定，部署就是 `git push`。

型別檢查靠 `jsconfig.json` 的 `checkJs` 加 JSDoc（`js/types.js` 是資料模型的
單一定義處），VSCode 內建的 TypeScript 服務會即時檢查——有型別安全但零 build。
要在命令列跑一次：

```sh
npx -y -p typescript@5.7 tsc -p jsconfig.json --noEmit
```

```
index.html
privacy.html / terms.html  OAuth 同意畫面要求的連結
css/app.css              手寫 CSS + design token，只做亮色主題
vendor/                  SheetJS 與 ECharts，vendored 不用 CDN
js/config.js             Google 憑證與分頁名稱
js/types.js              資料模型的 JSDoc @typedef
js/auth.js               GIS token client + Google Picker
js/drive.js              files.get?alt=media
js/store.js              localStorage 快取 + 載入流程
js/parse/                xlsx → 正規化 model（解析的複雜度都在這裡）
js/parse/adjustments.js  非交易的股數異動（分割、員工購股、配股）
js/model.js              換匯、跨券商合併、衍生指標
js/market.js             歷史股價（FinMind / TWSE）+ localStorage 快取
js/charts.js             ECharts 主題 + option builder + mount/dispose
js/views/parts.js        hero / stat tile / 篩選列 / 帶長條的表格欄
js/views/{overview,assets,positions,pnl,trades,selftest}.js
js/selftest.js           對照試算表的斷言
js/boot.js               外殼：登入閘門、分頁、錯誤→人話
ops/web_serve.py         本機開發用的 no-cache server
```

分頁：**總覽**（hero + KPI + 總報酬 + 配置 + 各券商 + 前 10 大）、
**資產走勢**（期間篩選 + 曲線 + 堆疊面積 + 佔比 + 每日變化 + 匯率）、
**持股**（treemap + 損益排行 + 泡泡圖 + 明細表）、
**損益**（年度堆疊 + 累積 + 個股排行 + 交易成本 + 除權息）、
**交易明細**（個股搜尋 + **K 線覆盤** + 統計）、
**自我測試**。

除錯用的深連結：`?tab=<id>`、`?symbol=2330`。

## 歷史股價（K 線覆盤）

`js/market.js` 直接從瀏覽器抓日 K，不需要伺服器。實測結果：

| 資料源 | CORS | 用途 |
|---|---|---|
| **FinMind v4** | `Access-Control-Allow-Origin: *` ✅ | 主要來源，**免 token**。`TaiwanStockPrice` 一次請求涵蓋上市/上櫃/ETF，`USStockPrice` 涵蓋美股 |
| **TWSE STOCK_DAY** | `Access-Control-Allow-Origin: *` ✅ | 台股備援（額度用完時）。一個月一次請求、民國年日期、數字帶逗號 |
| Yahoo v8 chart | — | 回 429，不可靠 |
| TPEx 新站 / Stooq | 無 ACAO ❌ | 瀏覽器直接擋掉 |

### 台股是原始價，美股不是

這個不對稱比這一節其他任何事都重要，而且是實測出來的：

- **`TaiwanStockPrice` 回原始價。** 0050 在 2025-06-18 做 1 拆 4，它的序列在該日從
  ~190 跳到 ~47.5（沒有回頭改寫歷史）。工作簿裡每一筆台股成交**全部**都落在
  各自當天的高低區間內，不需要任何換算。
- **`USStockPrice` 會改寫歷史。** 2025-06-16 它回報 IBKR 收盤 52.42，
  而工作簿記的當天成交價是 **204.66**——正是兩天後 4:1 拆股的倍率。

所以「把標記畫在成交價上」在台股是對的，在那檔美股上會**高四倍**，
而且序列本身看不出來——還原過的序列沒有跳空可以偵測。

**`alignTrades()` 補掉這個洞，而且兩個市場都不需要分割資料表**：它逐筆問
「哪一個整數倍率能把這個成交價放進當天的實際高低區間」。實務上答案唯一
（IBKR 的 204.66 對上 [51.10, 52.74]，只有 4 成立），這是**約束求解而不是推論**。
它也必須容忍成交價因為正常原因落在區間外——零股交易的價格會落在盤中區間之外，
0050 在 2026-01-15 的 68.75 對上 [70.15, 70.70] 就是這種情況——所以小幅偏離
維持倍率 1，不會被誤判成公司行為。

得到的倍率同時是**股數乘數**：需要 ÷4 才對得上還原序列的成交，
表示它記錄的是分割前的股數，所以 ×4 就是今日單位。

### 分割與減資：試算表自己就有（最權威）

`adjustments` 分頁列出**每一筆不是交易的股數異動**，這讓工作簿變成自洽的：

```
Σ(交易股數 × 分割倍率) + Σ(異動股數)  ==  券商庫存
```

實測**每一檔都成立**，最大誤差不到千分之一股（券商贈股的股數在上游是用相減反推的，
留下一個四捨五入殘差）。`?selftest=1` 把這個恆等式當成斷言——它是整份檢查裡最強的一條，
而且**不需要任何期望值檔案**。在這個分頁存在之前根本無法驗證：有員工認股的標的，
交易紀錄的淨額與券商回報的庫存差了好幾倍，而檔案裡沒有任何地方說明為什麼。

三種類型：

| 類型 | 意義 | 關鍵欄位 |
|---|---|---|
| `股票分割` | 換算單位，不增減股數 | `分割比例` |
| `股數補登` | 券商回報之外進來的股（員工認股信託撥轉、開戶贈股） | `股數異動`、`每股成本` |
| `配股` | 除權配股，成本 0 | `股數異動` |

⚠️ **`股數單位` 欄決定分割要不要再套用一次。** `今日` 表示該數字已經是今日單位，
後續分割**不可**再乘（AssetSync 已經乘過了）；`當日` 表示是當時單位，後續分割仍要乘。
讀反的話會把補登股數乘四倍。

這個分頁也涵蓋**美股**（IBKR 2025-06-18 的 1 拆 4），而 FinMind 沒有美股分割 dataset——
所以 IBKR 的均價不再需要推論。

### 分割與減資：台股還有 FinMind 官方資料

`TaiwanStockSplitPrice` 直接給官方的分割前後參考價，兩者的商數就是精確倍率
（0050：188.65/47.16 = 4.000；00631L：443.15/20.14 = 22.003），**沒有混進當天的
價格變動**。`TaiwanStockCapitalReductionReferencePrice` 涵蓋減資。
美股沒有對應的 dataset，所以那邊只能靠上面的逐筆對齊。

⚠️ **不要從價格跳空反推倍率。** 那個跳空是「分割倍率 × 當天自己的價格變動」的乘積。
以 00631L 為例，收盤 443.15 → 19.26：若是 1 拆 22 則當日 −4.4%，若是 1 拆 23 則
−0.04%，兩者都在漲跌幅限制內。商數說 23，實際是 **22**。所以圖上的標線只有在拿到
官方倍率時才寫「1 拆 22」，否則只寫「價格不連續」。

### 歷史買入均價怎麼算

`累計金額 ÷ 累計股數`（不是把價格欄直接平均）。分子沒問題——金額是分割不變量。
**問題在分母**：試算表記的股數是「成交當天的單位」，跨過分割之後同一檔的「股」
不是同一個單位（0050 分割前的 1 股等於之後的 4 股）。

所以每一筆的股數都會先用倍率還原成今日單位才相除。倍率來源依權威性排序，
**每檔只用其中一個**，避免同一次分割被套用兩次：

1. **試算表的 `adjustments` 分頁** —— AssetSync 實際用的比例，且涵蓋美股。
2. **FinMind 的台股官方分割參考價** —— 補上 AssetSync 沒追蹤的分割。
   AssetSync 只記錄它自己 FIFO 需要的分割，而在分割前就已清倉的部位（00631L）
   不在分頁裡。
3. **逐筆對齊當日行情** —— 前兩者都沒有時的最後手段。

減資擋在中間時顯示「—」，因為現金減資的參考價同時吸收了退還的現金，
股數比例無法從中還原。

差距不是小數點後的問題：跨過一次 1 拆 4 的分割，未還原的均價可以比正確值高出三成；
跨過 1 拆 22 的，可以高出一倍以上。

### 個股頁會把差額拆成具名事件

有了 `adjustments`，「交易紀錄的淨股數對不上券商庫存」不再只能給一句
「差額來自配股、員工認股或股票分割」的通則，而是直接把每一筆異動的日期、類型與股數
列出來，並附上分頁裡 AssetSync 自己寫的推導說明（例如某筆股數是「由某天賣出時的
部位缺口反推得出」）。恆等式若對不上，畫面會直接說「差額無法由試算表現有資料解釋」，
而不是把它藏起來。

## 圖表規則

`js/charts.js` 把規則集中實作一次，所以「細長的 mark、髮絲級網格、2px 線、
資料端 4px 圓角、堆疊之間 2px 底色間隙」是結構上成立，不是靠記得。幾條不可協商的：

- **永遠不用雙 Y 軸。** 兩個不同尺度疊在一起會製造出資料裡沒有的相關性，
  強弱只取決於兩個軸怎麼對齊。所以 USD/TWD 匯率是獨立的一張小圖，
  不是資產曲線的右軸。
- **類別色固定槽位、永不循環。** 顏色跟著實體（券商），所以篩選不會讓存活的
  序列重新上色。超過 8 個就併成「其他」。
- **文字永遠不穿資料色。** 軸標籤、數值、圖例都用 ink token；辨識來自旁邊那個
  有顏色的 mark。唯一例外是填色區塊內的標籤，由填色亮度決定黑白。
- **漲跌色是紅漲綠跌，而且永不是唯一通道。** 紅綠配對過不了色盲檢測
  （實測 CVD ΔE 4.4，低於門檻），所以每張用到它的圖都同時用**位置**表示正負
  （棒子從 0 基準線往上/下、往左/右），並直接標上帶正負號的數字。
- **兩個以上序列一定有圖例**，一個序列則沒有（卡片標題已經說了畫的是什麼）。
- **價格用點圖或 K 線，不用柱狀圖。** 價格軸不能從 0 開始，而柱子的長度會被讀成
  數值，在截斷的軸上會把價差放大。點與 K 棒只主張位置與範圍，所以非零軸對它們是
  誠實的。
- **價格與成交量是兩個上下並排的面板，不是雙 Y 軸。** 共用一條 X 軸的
  small multiples 是規範認可的作法。
- **買賣標記畫在當天 K 棒上「實際成交的那個價位」**，不是浮在棒子上下。
  這張圖存在的意義不是「那天有沒有交易」，而是「在那天的振幅裡成交在哪個位置」。

配色是驗證過的：類別槽位相鄰最差 CVD ΔE 9.1、正常視覺 ΔE 19.6，
順序本身就是色盲安全機制，不要重排。

## 這份資料算不出來的東西

儀表板很想把資產成長拆成「我投了多少」與「市場給了多少」。
**這份資料做不到，硬做會產生一個很有信心的錯誤數字。**

交易紀錄記的是券商帳戶**內部**的現金移動：買進 10 萬的股票，是把 10 萬從
交割款移到持股，總資產不變。所以 trades 的淨現金流不是對外投入。
真正的存入與提出沒有記錄在試算表任何地方，而 history 的每日變化是

```
Δ總資產 = 市場漲跌 + 收到的股利 + 對外轉帳
```

第三項無法分離。同樣的缺口也讓資金加權報酬率（IRR/XIRR）算不出來，
因為它需要的正是那些對外現金流。

站得住腳的是券商分頁直接給的數字：**總報酬 = 未實現 + 已實現 + 除權息**，
所以那是首頁的頭條數字；資產曲線則明確標示為「帳戶餘額的歷史」，不是績效。

## 本機開發

```sh
copy "<你的 Drive 同步資料夾>\AssetSync.xlsx" dev-data.xlsx   # gitignored
python ops/web_serve.py
```

- <http://127.0.0.1:8899/index.html> — 正常流程（需要先完成下面的 Google 設定）
- <http://127.0.0.1:8899/index.html?dev=1> — 離線模式：讀本機 `dev-data.xlsx`、跳過 Google
- <http://127.0.0.1:8899/index.html?dev=1&selftest=1> — 自我測試（刻意不在分頁列上，
  只能用這個連結進入；它是診斷工具不是儀表板）

`?dev=1` 讀的是 xlsx 本身而不是預先解析好的 JSON，所以它會跑**真正的 parser**——
複雜度都在那裡，這條路徑才測得到。

**不要用 `python -m http.server`。** 它不送 `Cache-Control`，瀏覽器會啟發式快取，
結果同時服務新舊版 ES module；症狀是某個明明正確的檔案報
`Cannot read properties of undefined`。`ops/web_serve.py` 存在的唯一理由就是
強制 `no-store`。

## Google 設定（一次）

在 Google Cloud Console：

1. **APIs & Services → Library** 啟用 **Google Picker API** 與 **Google Drive API**
2. **Credentials → Create credentials → OAuth client ID → Web application**
   - Authorised JavaScript origins：`http://localhost:8899`、
     `http://127.0.0.1:8899`、`https://dave851221.github.io`
   - Redirect URIs 留空（token flow 不用）
   - 把 client ID 填進 `js/config.js` 的 `GOOGLE_CLIENT_ID`
3. **Credentials → Create credentials → API key**，限制到上面那些 origin 與 Picker API，
   填進 `GOOGLE_API_KEY`
4. `GOOGLE_APP_ID` 是 GCP 的**專案編號**（Project number，不是 Project ID 也不是名稱），
   在 Console 首頁的 Project info 卡片上。它也就是 client ID 開頭那串數字——
   **三個值必須來自同一個專案**。對不起來的話，Picker 照樣開得起來、也照樣回傳檔案，
   但之後每次讀那個檔案都會 404，因為授權給了另一個 app。
5. **OAuth 同意畫面**（新版 Console 在 **Google Auth Platform → Audience**）：
   User type 選 External，填好 App name、support email、developer contact。
   然後在 **Test users** 按 **+ Add users** 把自己的 Google 帳號加進去 —— 不加的話
   登入會被擋在 `403: access_denied`（「未完成 Google 驗證程序」），即使你就是專案擁有者。

   留在 **Testing** 狀態就夠用了。它的兩個限制對單人工具都不痛：100 人上限（使用者只有你）
   與「只有名單內帳號能存取」（那正是我們想要的）。至於測試模式下 refresh token 七天過期，
   本專案用 implicit token flow、根本沒有 refresh token，所以完全不受影響。

   想改成 production 的話，「發布應用程式」按鈕會被品牌頁卡住，必須先填三個連結
   （都要落在授權網域底下）：首頁 `/asset-web/`、隱私權政策 `/asset-web/privacy.html`、
   服務條款 `/asset-web/terms.html`。這三頁在 repo 裡已經備好了。

   ⚠️ **品牌頁的「應用程式標誌」永遠不要上傳。** 一上傳就會強制送交 Google 驗證，
   把只用非敏感 scope 換來的免審查優勢整個吐回去。

Scope 只用 `drive.file`。這是**非敏感 scope**，所以不需要 Google 驗證審查、
沒有 100 位測試使用者上限、也不會出現「此應用程式未經驗證」警告。
代價是必須用 Picker 選一次檔案——而那正是權限閘門本身。
**不要改成 `spreadsheets.readonly` 或 `drive.readonly`**，一加敏感 scope，
審查與人數上限就全部回來。

`js/config.js` 裡的三個值**可以安全 commit**：它們只識別應用程式、不授權任何東西，
真正的防線是 OAuth client 的 origin 限制。這個專案沒有任何真正的機密。

## 部署

repo 必須是 public（Pages 免費層的限制），所以：

- **真實資料永不進 repo。** `.gitignore` 已排除 `dev-data.xlsx`。
  推之前確認一下：`git ls-files | grep dev-data` 應該是空的。
- 推到 public repo → Settings → Pages → 從 `main` 的根目錄發布
- 把 Pages 網址加進 OAuth client 的授權來源

過了登入閘門之後，使用者可以從 DevTools 看到完整的 model JSON。
**前端隱藏欄位不算保護**，這點是明確接受的——反正資料本來就是他自己的。

## 資料的坑

試算表有二十幾條會讓數字算錯的陷阱，全部寫在 `js/parse/` 各檔的檔頭註解裡。
最容易咬人的幾條：

- **空白 cell 是 `null`，不是 0。** 停用的券商、未解出的 FIFO 成本都是空白。
- **`—`（U+2014）是「無值」標記**，而且那些 cell 仍帶 `#,##0` 數字格式。
- **數字欄可能是一句話**：`已實現損益` 會是 `請填入 cost_override.json`。
- **百分比已經是小數**（`0.2479` = +24.79%），不要再除 100。
- **券商分頁是多區塊文件，不是表格。** 列號會隨年度、券商、註腳而位移，
  只能掃 A 欄找區塊標題。`小計` 標籤所在的欄位每個區塊還不一樣。
- **`history` 的「富邦現金」是餘額 + T+2 待交割**，與券商分頁的「交割戶餘額」
  本來就不同，兩者對不上是預期行為。
- **`summary` 的個股彙總會丟掉已下市股票**，所以它的總市值對不上券商分頁。
  本專案保留並標記 `delisted`。
- **富邦的手續費與交易稅是估算值**（0.1425%、NT$20 下限），永豐與 IBKR 是實際值，
  而試算表沒有標記哪個是哪個。
- **`adjustments` 的表頭不在第 1 列**（第 1 列是一段合併儲存格的說明文字），
  所以要掃第一欄找「日期」而不是假設列號。
- **定期定額與股利再投資已進入 `trades_YYYY`**，委託號碼是 `M_DCA_*` / `M_DRIP_*`
  的合成編號（`M_` 表示不是券商回報的原始委託）。

## 自我測試（`?selftest=1`）

`js/selftest.js` 是這個專案的測試，跑在瀏覽器裡。**刻意不放在分頁列上**——它是診斷
工具不是儀表板；用 `?selftest=1` 或 `?tab=selftest` 進入。

**每一項檢查都不依賴手抄的期望值。** 試算表每天重新產生，所以把當下的總資產、
市值、筆數抄下來當期望值，隔天就全部過期；早期版本把這些數字放在一個 gitignore 的
JSON 裡，那是錯的形狀。現在對照的是三種東西：

1. **試算表自己算的小計。** 每個券商區塊都以 `小計` 收尾，而 parser 刻意跳過那些列
   不當資料讀。「我逐列加總的結果」對上「Excel 算的總數」就是兩個獨立程式得到同一個
   答案，而且對照組數會隨區塊自動增加。
2. **資料內部的恆等式。** 持股必須能由「交易紀錄 × 分割倍率 + 非交易異動」還原；
   `history` 的 `資產變化` 必須等於相鄰兩列總資產之差。
3. **不隨資料變動的結構規則。** `—` 變成 `null` 而不是 0、百分比沒有被重複縮放、
   券商分頁維持原幣、台股代號沒掉前導零、分割倍率在分割當日就是 1……

所以這頁上線後仍然有用：它跑的是你剛剛載入的那份試算表。萬一 AssetSync 改了某個欄位
而 parser 開始靜默讀錯，這裡會變紅。

⚠️ **不要把實際數字寫進 repo。** 這個 repo 是公開的，而餘額、市值這類數字既是
驗證資料也是個人財務資訊。上面三類檢查都不需要它們。
